## 2. `DrachnyenAbility$$ExecuteBehaviour` — lecture

```
hpNode  = Direct( GetVariableForLevel(config@0x60, 0x1d = hp, abilityState) )   # == ...$$HealthAmount
maxHp   = StatAmount( Owner@0x148, 5 = Health, 2 = MAXIMUM, 0 )
[1] setHp  = ChangeStat( Owner@0x148, Position(5 = Health, 0), mode 0 = SetAbsolute,
                         Min(maxHp, hpNode) )                                  # == ...$$GetSetHealthBehaviour
[2] addEff = AddEffect( 0x5bf = 1471 Drachnyen_ExtraAttack, AbilityStateReference,
                        targets = Owner@0x148, options ZERO )
[3] attack = UseActiveAbility( subject = Caster@0x160, targets = Target@0x178,
                               abilityType = UnitNormalAttackType(Caster@0x160),
                               source = AbilityOrEffect(this+0x10 = 0x405), <opts> )
AActiveAbility.Execute( op_BitwiseAnd( op_BitwiseAnd([1], [2]), [3] ) )
```

Trois lectures qui ne se devinent pas :

- **`ChangeStat` mode 0 = SetAbsolute.** L'appel a EXACTEMENT la forme de
  `BlackRageAbility$$GetSetHealthBehaviour` (même overload `DSLFactory$$ChangeStat`, même
  `Position(5,0,0)`, même 4ᵉ argument `0`) — or ce dernier est live-validé bit-exact (case-217).
  Le `3` visible au décompilé (`CONCAT44(uVar4,3)`) est le 7ᵉ argument (`ChangeStatBehaviour+0x78`,
  GroupType), **pas** le mode (`+0x68`, le 4ᵉ argument, qui vaut `0`).
- **`Min` = un CAP, et le SET peut FAIRE PERDRE des PV.** `hp` est rarity-scaled et peut dépasser le
  MaxHealth réel — i2 : « Abaddon cannot be set to higher Health than his maximum Health ». Et dans
  l'autre sens : mesure live rank 17, Abaddon **10038 → 6480 PV**, soit une PERTE de 3558. Porter un
  `max(hp, courant)` (réflexe « c'est un heal ») serait faux dans le sens le plus visible.
- **Overload 5-args d'`AddEffect`.** `AddEffect(dsl, 0x5bf, abilityStateRef, Owner@0x148, 0)` passe
  par `DSLFactory$$AddEffect` **5 paramètres** (`@180de6e20`), qui appelle
  `AddEffectBehaviour..ctor(…, source = 0, targets = Owner@0x148, …)` : le sélecteur SOURCE est nul,
  et `AddEffectBehaviour$$Execute` retombe alors sur la cible (`lVar14 = lVar7; if (lVar8 != 0)
  lVar14 = lVar8;`). L'effet est donc posé **sur Abaddon**, source = Abaddon. (L'overload 6-args
  `@180de6bb0`, celui qu'utilise Herald, aurait mis `targets = 0` → `Execute` lève.)

Ordre : `[2]` pose l'effet **AVANT** `[3]`. La triggered `Drachnyen_ExtraAttackAbility` (1485), gatée
`HasEffect(Owner, 0x5bf)` sur `On(0x26 = NormalAttack)`, fire donc **dès l'attaque normale de CE
cast** — cascade live : `Drachnyen` > `Drachnyen_ExtraAttack` > `Loki_NormalAttack`.

## 3. `HeraldOfTheApocalypseAbility$$ExecuteBehaviour` — lecture

```
hits    = GetNumberConstant(config@0x60, 0x2f = nrOfHits)                      # 2
profile = GetDamageProfile(config@0x60)                                        # Piercing
tgtTile = First( SortByDistance( Tiles(Target@0x178), CasterTile@0x168 ), 1 )
line    = TilesBehindInLine( from = CasterTile@0x168, to = tgtTile,
                             settings{+0x10 = 1 checkWalkable, +0x11 = 1 updateReference},
                             maxCount = Get(2) @dsl+0xc8 )
behind  = Enemies( Owner@0x148, Units(line, 1, 3) op_Subtraction Target@0x178, 3 )
targets = Target@0x178 op_Addition behind
[1] AttackWithAttackDamage( Caster@0x160, targets, MinMaxDamage(this, level), Direct(profile),
                            Direct(hits), AbilityOrEffect(0x3fc), <opts> )
[2] AddEffect( 0x403 = 1027 HeraldOfTheApocalypse, AbilityStateReference,
               source = Owner@0x148, targets = targets, options ZERO )
[3] TriggerAbility( Enemies( Owner@0x148, SurroundingUnits(Target@0x178,
                              GetNumberConstant(0x16 = range) = 2, 1, includeCenter = 1, 3), 3 ),
                    0x401 = TriggeredAbilityType.BattleFatigue,
                    actor@0x158, caster@0x160, target@0x178, null, 3, false )
AActiveAbility.Execute( op_Addition( op_Addition([1], [2]), [3] ) )
```

- **« directly behind » = UNE tuile, pas un anneau, pas un cône.** `TilesBehindInLine(from =
  CasterTile, to = tuile de la cible, maxCount = Get(2))` rend `[tuile cible, tuile derrière]` (la
  1ʳᵉ tuile rendue EST `to`) ; `settings{1,1}` active le gate walkable **et** le gate d'élévation
  pas-à-pas (`|Δelev| < 2`). ⚠ Ne PAS confondre avec `UnitsDirectlyBehind` (Supercharge/PlasmaCannon),
  qui rend jusqu'à N unités d'un cône.
- **Le filtre d'équipe est porteur de sens** : `Enemies(Owner@0x148, …)` — un **allié** du caster
  debout derrière la cible n'est PAS frappé (discriminant testé). `op_Subtraction Target()` retire la
  cible du 2ᵉ volet, `op_Addition` la remet en tête.
- **`Get(2)` = `dsl+0xc8`** : le `DSLFactory..ctor` alloue `+0xb8 = Get(0)`, `+0xc0 = Get(1)`,
  `+0xc8 = Get(2)`, `+0xd0 = Get(100)`, `+0xd8 = Get(-1)`. Lu, pas déduit.
- **`0x401` est un `TriggeredAbilityType`, PAS un `ActiveAbilityType`.** `TriggeredAbilityType.
  BattleFatigue = 1025` ; `ActiveAbilityType[1025]` vaut `SkyStrike` (Sisterhood) — l'enum non
  qualifiée aurait fait porter un airstrike de Celestine. `DSLFactory$$TriggerAbility` a deux
  overloads ; Herald passe le `0x401` en `undefined4` → celui de `@180dfe670`.
- `armorReduction` (variable de la config 1020) n'est lu NI par cet `ExecuteBehaviour` NI par
  `HeraldOfTheApocalypse_ExtraDamageEffect` : variable morte pour la face COMBAT (notée, pas portée).

### 4bis. Les deux données de registre (cliquet `test_ability_registry_ratchet.py`)

Les deux ctors **cumulent les deux pièges à masque** connus, et **divergent** — d'où une lecture
ability par ability :

| | `<X>Ability$$.ctor` | masque EFFECTIF | `AbilityAttackType` |
|---|---|---|---|
| 1020 Herald | recopie le preset statique `TargetingOptions statics+0x40`, **aucun** appel de ctor | `0x4000` = `TargetIsEnemy` | `0` DirectTargetAttack |
| 1029 Drachnyen | MÊME preset, passé à l'overload **PRESET + flags** `(&out, &preset, 0x200000000)` | `0x200000000 \| 0x4000` = `0x200004000` = `TargetIsEnemy \| TargetIsNotAnObject` | `0` DirectTargetAttack |

Le masque de Herald n'apparaît **nulle part** dans son ctor : il est écrit par
`IdunBattle.Core.Services.TargetingOptions$$.cctor` à `<preset>+0x28`. Celui de Drachnyen n'est pas
le littéral visible : l'overload `TargetingOptions..ctor(dest, preset, flags)` fait
`dest.Rules = flags | preset.Rules` et recopie le reste verbatim.

**PORTÉE** — le même `cctor` écrit pour ce preset `+0x40` : `Range` ← `TargetingRange statics+0x30`
(`onlyAdjacent = True`, `overrideRange = 1`) et `forceMeleeTarget = 1` (`RangedBool.False`). Les deux
abilities exigent donc une cible **ADJACENTE**, et la constante `range` de leur config n'est PAS la
portée de ciblage (`overrideRange` déjà posé court-circuite
`AActiveAbility$$SetConfigValuesInTargetingOptions`) — pour 1020, `range = 2` ne sert qu'au disque
`SurroundingUnits` du volet BattleFatigue. C'est le MÊME preset que `JakhalStimms` (1131), et il est
distinct de celui des actives DarkAngels/Aeldari (`statics+0x140`, `Rules = 0x4002`).

`AbilityAttackType = 0` pour Drachnyen **bien que son behaviour n'attaque pas en direct** (il
dispatche l'attaque normale via `UseActiveAbility`) : on transcrit le 3ᵉ argument du ctor, jamais le
profil de dégât de l'arbre.
